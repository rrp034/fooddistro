Trojan Horse (value semantics as opposed to reference semantics).

Bob and Sally are getting married in 6 months but need a little more money for the honeymoon and beyond. The company Sally works for has hired the company Bob works for to write a routine to calculate gross pay, taxes, insurance, net pay etcetera. The basic logic follows.

Loop until EOF Get next employee master record including hours worked, payrate and other employee data from payroll file. Execute Bob's routine passing all information by reference returning gross, insurance, taxes and other information. Write check/direct deposit net pay. Provide employee desired payroll information. Add merit, incentive and other emoluments to payroll record for next pay period. Update the employee master record to reflect the current pay period. End loop

Bob's program should never modify the salary, payrate or hours worked. Bob and Sally have agreed he should give her a 10% raise every pay period and increase the hours she worked by 12%. If anyone ever notices the behavior of her paycheck, they cannot be prosecuted. The master pay record will show Bob's calculations to be accurate in the last pay period due to the update by Sally's company (erases previous information). This is an example of the Trojan Horse. Bob's routine was invoked for a necessary service. If the payrate and hours worked had been passed by value Bob and Sally would be in great trouble. Sally's company could not stop a single paycheck from manipulation. However, the payrate and hours in the master record would not have been modified and would not stand up to scrutiny in an audit. In Go, you can control this by passing copies of structs (value semantics) versus pointers (reference semantics).

Step Function:

Step functions are a common practice in computer simulations to determine things like the number of items a person purchases in a store. This determines the amount of time required for checkout at the register, hence the number of employees required in a specific period as checkers (also checkout lanes). It also helps determine the number of fast checkout lanes required to augment the general lanes accommodating filled shopping carts. Statistics are normally gathered from a physical count of baskets or typical transactions from the log generated by the register. For example, we may find customers can be grouped as 25% purchase 1 to 3 items, 45% purchase 4 to 10 and 30% have full carts. Each group requires approximately the same time at the register. This can be mimicked on a computer using a uniformly distributed random number generator where the random deviates are greater than or equal to zero and less than or equal to 1.0.

Exponential/Poisson Distributions

We will assume freight Starships with food arrive at a constant rate in the system at a rate of one every two hours. This is a traditional Poisson random distribution. Rather than using the Poisson distribution directly, it is frequently more convenient to schedule arrivals based on their interval between arrivals using the exponential distribution. That way goroutines can sleep when not needed.

It is easy to abuse the Poisson and Exponential distributions. Consider the student center in a fall or spring semester. The arrival rate at Starbucks is very high during the 15 minutes prior to and after class change. The arrival rate is much lower during other periods. The same may be true at traffic lights during rush hours. You will need differed average arrival rates or perhaps better a custom arrival distribution.

Poisson distribution - Wikipedia

In probability theory and statistics, the Poisson distribution (/ˈpwɑːsɒn/) is a discrete probability distribution that expresses the probability of events occurring in a fixed interval of time with a known constant mean arrival rate and independently of the time since the last event (random event).

The exponential distribution is a continuous probability distribution that describes the time interval between events in a process where events occur independently at a constant average rate. It determines the waiting time until the next event in a Poisson process. This distribution appears naturally in many scenarios---from equipment failure times, customer service wait times to radioactive decay.

Specification:

We must develop software to manage an inter-planetary food distribution system for use in multiple regional solar systems. The basic software currently consists of a food storage system (Warehouse referred to as the Gate Keeper (currently utilizing a circular queue) and food sales (points-of-sale, POS). The Gate Keeper only services one request at a time to prevent "race conditions." Arriving food shipments (multiple independent goroutines -- simulate arriving inter-galactic freighters) will request storage space in the warehouse (M 1 relationship). If insufficient space is available, the food shipment should be routed to another system. Food Sales (N 1) (multiple independent goroutines supporting food distribution) provides access to food packets from the warehouse. The Food Sales prepares food for sale and completes the POS transaction. If the warehouse (Gate Keeper) receives multiple simultaneous requests for service (request for storage space) and/or multiple request for food packets (from sales), the request are serviced randomly (uniformly distributed fashion) to prevent system starvation.

The Gate Keeper and Food Sales software will be used as the final system. The Product Generators will be replaced in the final system by the physical arrival of food shipments from interstellar cargo ships over which we will have no control. To test the design and determine system flexibility, implementation must allow for multiple Product Generators (separate competing concurrent goroutines) and multiple Retail Sales (POS - separate competing concurrent goroutines) communicating with a single Gate Keeper to prevent race conditions.

// in file circularque/circularque.go // // The GateKeeper utilizes a circular queue for storage and retrieval. The package has been // designed to be generic to allow use in future systems with respect to the data type and queue size. // // The software suite consists of main.go, // food, stats, gatekeeper, // producer, circularque, and sales packages. // // This represents the software to manage an "embedded" planetary system // food receiving and distribution system. package circularque import ( "errors" "fmt" ) type CircularQue[T any] struct { capacity int box []T front, rear int mesnum int } func NewCircularQue[T any](capacity int) *CircularQue[T] { return &CircularQue[T]{ capacity: capacity, box: make([]T, capacity), front: 0, rear: 0, mesnum: 0, } } func (q *CircularQue[T]) AcceptMessage(msg T) error { if q.mesnum >= q.capacity { return errors.New("ERROR - Message rejected - queue is full!") } q.rear = (q.rear + 1) % q.capacity q.box[q.rear] = msg q.mesnum++ return nil } func (q *CircularQue[T]) RetrieveMessage() (T, error) { var zero T if q.mesnum <= 0 { return zero, errors.New("ERROR - No message in the queue to retrieve!") } q.front = (q.front + 1) % q.capacity msg := q.box[q.front] q.mesnum-- return msg, nil } func (q *CircularQue[T]) IsEmpty() bool { return q.mesnum == 0 } func (q *CircularQue[T]) IsFull() bool { return q.mesnum >= q.capacity }

// // The software suite consists of main.go, // food, stats, gatekeeper, // producer, circularque, and sales packages. // // The GateKeeper accepts FoodPacks from inter-galactic transports // and repacks them into FoodPacks suitable for Sales to // distribute to the planets in the system. package gatekeeper import ( "fmt" "time" "fooddistro/food" "fooddistro/circularque" ) type GateKeeper struct { queue *circularque.CircularQue[food.FoodPack] acceptChan chan food.FoodPack retrieveChan chan retrieveRequest rejected int startTime time.Time endTime time.Time } type retrieveRequest struct { response chan food.FoodPack available chan bool } func NewGateKeeper(capacity int) *GateKeeper { gk := &GateKeeper{ queue: circularque.NewCircularQue[food.FoodPack](capacity), acceptChan: make(chan food.FoodPack, 100), retrieveChan: make(chan retrieveRequest, 100), rejected: 0, startTime: time.Now(), endTime: time.Now().Add(40 * time.Second), // 40 seconds = 40 hours simulation } go gk.run() return gk } func (gk *GateKeeper) AcceptMessage(foodPack food.FoodPack) { gk.acceptChan <- foodPack } func (gk *GateKeeper) RetrieveMessage() (food.FoodPack, bool) { respChan := make(chan food.FoodPack) availChan := make(chan bool) gk.retrieveChan <- retrieveRequest{response: respChan, available: availChan} available := <-availChan if available { return <-respChan, true } return food.FoodPack{}, false } func (gk *GateKeeper) run() { time.Sleep(500 * time.Millisecond) // Allow initialization (0.5 seconds = 0.5 hours) for gk.rejected < 5 && time.Now().Before(gk.endTime) { select { case newFood := <-gk.acceptChan: if !gk.queue.IsFull() { gk.queue.AcceptMessage(newFood) fmt.Printf("GateKeeper insert accepted %s %c\n", newFood.FoodType, newFood.FoodShipment) } else { gk.rejected++ fmt.Printf("Rejected by GateKeeper:\n") fmt.Printf("%s %c\n", newFood.FoodType, newFood.FoodShipment) fmt.Printf("Rejected = %d. Sent to another distribution facility!\n\n", gk.rejected) } case req := <-gk.retrieveChan: if !gk.queue.IsEmpty() { foodItem, _ := gk.queue.RetrieveMessage() // Generate desired food type for management reporting mgtDesiredType := food.RandomFoodType() fmt.Printf("Mgt Desired Food Type To Sell is: %s\n", mgtDesiredType) fmt.Printf("Actual type sold is: %s\n", foodItem.FoodType) fmt.Printf("Food pack removed by GateKeeper for shipment.\n\n") req.available <- true req.response <- foodItem } else { req.available <- false } } time.Sleep(1100 * time.Millisecond) // Processing overhead (1.1 seconds = 1.1 hours simulation) } elapsed := time.Since(gk.startTime) fmt.Printf("\n\nHours of operation prior to closing: %.3f\n", elapsed.Seconds()) }
